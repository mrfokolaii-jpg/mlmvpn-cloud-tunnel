# نقشهٔ اقتباس بخش GitHub Tunnel

**مبنای بررسی:** `mlmvpn/mlmvpn_android`، شاخهٔ `main`، commit `fdb07a5d0a99ca6347bd3716b0f0783341bac16a`؛ بررسی‌شده در ۲۹ اکتبر ۲۰۲۶. مجوز مخزن مرجع: **GPL-3.0**.

## تصمیم معماری

اپ فعلیِ `mlmvpn-cloud-tunnel` حفظ می‌شود: Java، رابط بومی فعلی، `TunnelService`، `XrayEngine` و workflow/agent همین مخزن. فایل‌های Kotlin/Compose مرجع را به‌صورت drop-in کپی نمی‌کنیم؛ آن‌ها به سرویس VPN اصلی MLMVPN، حساب‌های Cloudflare، Compose، SecureStore/TweetNaCl و اسکنر IP آن برنامه وابسته‌اند. رفتارهای لازم را با اجزای موجود این پروژه اقتباس می‌کنیم. در پیاده‌سازی این مرحله کد GPL مرجع عیناً منتقل نشده است؛ اگر بعداً بخشی از آن عیناً منتقل شود، باید انتساب و تعهدهای GPL-3.0 برای توزیع رعایت شوند.

## وضعیت اپ فعلی و شکاف‌ها

- `GithubApi`, `ManagedProvisioner`, `OAuthTokenManager` و `TokenVault` ورود device-flow، مخزن خصوصی و workflow را انجام می‌دهند؛ توکن با Android Keystore رمز می‌شود.
- `Settings` مخزن هر نام کاربری را جدا نگه می‌دارد، اما نسخهٔ اصلی فقط یک توکن/حساب فعال داشت؛ `RunStore` نیز run را به مخزن و شناسه وصل می‌کرد، نه به حساب مالک توکن.
- `TunnelService` و `XrayEngine` یک نشست را اجرا می‌کنند و کشور را هنگام ساخت نشست می‌گیرند. درخواست کشور فقط وقتی پذیرفته می‌شود که خروجی VPN Gate و کشور مشاهده‌شده تأیید شود؛ fallback بی‌صدا به runner مجاز نیست.
- اپ فعلی Cloudflare OAuth/Worker ندارد و از رله‌های عمومیِ بسته‌بندی‌شده در agent استفاده می‌کند.
- مسیر TUN فعلی `hev-socks5-tunnel → SOCKS → Xray` است. قوانین دامنه را می‌توان در Xray ارزیابی کرد؛ قوانین مبتنی بر UID اپ، مانند مرجع، بدون انتقال به ورودی TUN/مسیر‌دهیِ UID-aware تضمین‌پذیر نیستند. این بخش باید پیش از پیاده‌سازی با نمونهٔ کوچک و آزمون روی دستگاه اعتبارسنجی شود.

## مراحل و معیار پذیرش

### مرحلهٔ ۱ — چند حساب GitHub و جداسازی امن

1. افزودن فهرست حساب‌ها با انتخاب حساب فعال و امکان افزودن/حذف حساب؛ توکن هر حساب جدا و رمز‌شده در Keystore باقی بماند.
2. مهاجرت نصب‌های تک‌حسابی فعلی بدون پاک‌شدن توکن یا مخزن ذخیره‌شده.
3. ثبت مالک حساب کنار هر run؛ لغو هر run فقط با توکن همان حساب انجام شود. هیچ توکنی در log، intent، workflow input یا فایل مخزن نرود.
4. تشخیص «سهمیه/محدودیت صریحاً تمام شده» از خطای شبکه، مجوز یا خطای خروجی. چرخش خودکار فقط روی پاسخ صریح سهمیه در مرحلهٔ dispatch انجام شود؛ خطای مبهم 403 باعث استفاده از حساب دیگر نشود.
5. نمایش حساب فعال و سلامت/وضعیت استفاده در UI. خواندن جزئیات billing فقط در صورت مجوز لازم و با رضایت آگاهانه؛ افزودن scope گستردهٔ `user` پیش‌فرض نیست.

**پذیرش:** آزمون مهاجرت تک‌حسابی، جداسازی repo/token، چرخش فقط روی quota قطعی و لغو با مالک درست؛ CI و آزمون‌های JVM سبز.

### مرحلهٔ ۲ — مسیر اختیاری Cloudflare Worker

1. طراحی اتصال Cloudflare با دسترسی محدود و ذخیره‌سازی رمز‌شده؛ هیچ API token یا client secret در APK، log یا مخزن قرار نگیرد.
2. استقرار Worker نسخه‌دار و امضای درخواست‌ها؛ Worker فقط relay همین نشست را به میزبان تونل وصل کند.
3. افزودن سنجش محدود IPهای احتمالی از مسیر واقعی (TLS/SNI/Host با نام Worker واقعی) و cache جدا برای Wi‑Fi/داده.
4. Worker مسیر اضافه بماند؛ رله‌های فعلی حفظ شوند و شکست Worker باعث fallback بی‌صدا به کشور/خروجی ناخواسته نشود.

**پذیرش:** آزمون صحت نسخه و امضای Worker، ردّ Host دلخواه و replay، timeout محدود، تست مسیر TLS؛ بررسی دستی بدون افشای credential.

### مرحلهٔ ۳ — خروجی زنده، دامنه و اپ

1. درخواست خروجی کشور از کانال وضعیت نشست، بدون ساخت مجدد workflow؛ تعویض UUID/route فقط پس از آماده و تأییدشدن IP/کشور خروجی.
2. افزودن قوانین دامنه در Xray با ترتیب و precedence روشن؛ خروجی آماده‌نشده نباید به مسیر مستقیم یا کشور اشتباه سقوط کند.
3. برای قوانین اپ، ابتدا اثبات کنیم تونل UID مبدأ را حفظ می‌کند. اگر SOCKS/TProxy فعلی UID را در اختیار Xray نمی‌گذارد، مهاجرت کنترل‌شده به ورودی TUN/route UID-aware لازم است؛ تا آن زمان قابلیت app-rule نمایش داده یا ادعا نشود.
4. تست‌های نشت: کشور دیده‌شده، UDP و DNS، شبکهٔ خصوصی/LAN، توقف/بازیابی و لغو نشست.

**پذیرش:** آزمون قواعد pure، سنجش واقعی کشور خروجی، نبود fallback ناخواسته، آزمون Android روی دستگاه برای UID routing و پایداری Stop/Start.

### مرحلهٔ ۴ — یکپارچه‌سازی و انتشار آزمایشی

اجرای `node --test tests/*.test.mjs`، آزمون‌های Android و build CI؛ بازبینی مجوزها و مجوزهای OAuth/Cloudflare؛ به‌روزرسانی README و نسخه؛ آزمون روی دستگاه و شبکهٔ واقعی. APK آزمایشی فقط پس از سبزشدن CI و باقی‌ماندن artifact قابل دانلود اعلام می‌شود.

## ترتیب اجرا

ابتدا مرحلهٔ ۱ (چند حساب و جداسازی runها)، سپس مرحلهٔ ۲ (Worker اختیاری)، و در پایان مرحلهٔ ۳ (خروجی زنده و قواعد؛ UID routing به‌عنوان زیرمرحلهٔ نیازمند اثبات). هر مرحله باید جداگانه آزمون و قابل بازگشت باشد؛ مسیر فعلی تا تأیید مسیر جایگزین حفظ می‌شود.

## پیشرفت این شاخه

مرحلهٔ ۱ پیاده‌سازی شده است: vault رمز‌شده و token refresh برای هر حساب جدا شده، حساب فعال و repo هر کاربر حفظ می‌شود، مهاجرت تک‌حسابی و مالکیت runها اضافه شده و لغو نشست با توکن صاحب همان run انجام می‌شود. چرخش محدود به پاسخ 403 با متن صریح مربوط به Actions quota در dispatch است؛ اپ endpoint خصوصی billing را صدا نمی‌زند و **هیچ چرخشی در خطای شبکه، مجوز مبهم یا نتیجهٔ نامشخص workflow انجام نمی‌شود**. حساب علامت‌خورده را کاربر می‌تواند دستی برای تلاش دوباره آزاد کند. آزمون Node (۱۲/۱۲)، آزمون‌های Android/JVM و ساخت APK در CI run `40890164170` موفق شدند؛ artifact `cloudpath-vpn-debug` (۵۴٬۷۶۰٬۸۸۶ بایت) موجود است. آزمون روی دستگاه واقعی هنوز انجام نشده. مرحله‌های Worker و مسیردهی سایت/اپ هنوز پیاده‌سازی نشده‌اند.
